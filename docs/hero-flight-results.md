# Hero flights: results of the final review

Review of 2026-11-21 and 22. It covers the library's flights (`flight` on
`SmoothClipView`, `SmoothClipFlightTarget`, window-space presentations and
`velocity: 'inherit'`) against Reanimated 4.8 shared element transitions (SET).
The behaviour contract is `docs/flight-spec.md`; how to measure is
`docs/hero-bench.md`.

**Evidence.** iPhone 18 Pro simulator (iOS 27.0, 60 Hz display), Expo 58,
React Native 0.88.1, Reanimated 4.8.0, react-native-screens 4.30.1, both
unpatched. Behaviour was checked in a Debug build, numbers come from Release
builds. Android ran on a Pixel 10 Pro emulator (API 37) for behaviour only.
No physical device was used.

## Benchmark

Two scenarios, 10 open/close cycles per cell, median (range). Release builds
on the iPhone 18 Pro simulator, 60 Hz. **Simulator numbers are relative**:
they compare the two pipelines on one machine and are not device numbers.

- **Push:** the card opens a detail screen with the native-stack slide, closed
  with the swipe-back gesture.
- **Sheet:** the card opens a detail screen as a page sheet, closed by
  dragging the sheet down.

How each column was measured (scripts in `docs/hero-bench.md`):

- **Mount time.** The trace build. The library logs the hardware timestamp of
  the touch-up; the screen recording gives the first frame in which the hero
  has left the card by more than 4 pt, a change the ease-in curve takes about
  40 ms to make. The recording's clock is placed on the touch's clock with
  the flights of the same recording (all 30 flights of each recording agree on the offset within 5 ms).
- **FPS, missed frames, longest frame.** The build without the trace. From the
  first moving frame to the first frame at the detail rect: frames the
  recording shows per second, display periods it skipped, and the longest gap
  between two frames. The recorder writes a frame per screen change.
- **Busy main thread.** The same, with 14 ms burned in every UI frame, the
  tap's frame included.
- **JS blocked.** The same, with the JS thread held for 300 ms from the tap,
  before it can request the navigation. Times from the trace build.
- **CPU.** Instruments' time profile over 10 cycles with no load, summed for
  the app's main thread and JS thread. Three runs of 10 cycles per cell; the table gives the median (range) of the three. Every figure includes 190–310 ms of the test driver's own main-thread work (argent reads the view hierarchy for each tap and wait). Most of the rest is the navigation and UIKit's transition, which both implementations pay. The transition's own main-thread code is 43–64 ms of SmoothClipView per 10 cycles for the flight, against 620–760 ms of Reanimated for SET (310–440 ms of it in the shared-transition code).
- **Memory.** The app's physical footprint, sampled five times a second over
  10 cycles that follow 10 warm-up cycles, then `leaks`. The growth and the
  leak records are the same for both implementations, so they belong to the
  app and its navigation, not to either transition. After the 120 flight cycles of the timing runs the heap held no carrier, keeper or snapshot view: only the window's flight layer, the coordinator and one pooled target view.

What it means: on the simulator both run at the display's 60 fps and miss no frame, with or without 14 ms of main-thread load. The flight shows motion about one frame sooner, and its start does not depend on the JS thread: with JS blocked for 300 ms it starts as usual, while SET starts 300 ms late. A whole open/close cycle costs the flight about 10–15 % less main-thread time, inside the run-to-run range for the sheet, and the same memory. None of this is a device measurement.

Checked and found sound:

- **Threads.** The start path has no synchronous JSI round trip, no
  `runOnUISync`, no lock held across UIKit calls and no wait on a React commit.
  A UI-thread start is one host function call; a JS start is `scheduleOnUI`.
- **Lift and landing.** Each is one `CATransaction` that moves one
  library-owned view: no forced layout pass, no drawing, no bitmap.
- **Per frame.** An iOS flight costs nothing per frame (Core Animation runs
  it). A gesture-driven way back costs one `setFrame` per frame.
- **Retain cycles.** The coordinator holds hosts and targets weakly, transition
  observers capture the host weakly, and the keeper that lands an orphaned
  flight is released by its animation's end.
- **Scaled ancestors.** A flight under a 0.9 scale starts and lands on the same
  pixels (XCTest). A rotated or skewed ancestor rejects window-space input and
  does not lift: the run plays in place.
- **Hosts that never fly.** On Android a run's start and end make one JNI
  call per host (`flightLift`, `flightRunEnded`) that returns after a field
  read; per frame, the host reads one field (`flight.carrierView`). On iOS the
  flight checks on the display and landing paths are ivar reads. A prop update
  converts `flightTag` to a string once per commit, never per frame.
- **Begin at install (iOS) and the stamp clamp (Android).** Every iOS run
  shares one `CACurrentMediaTime()` epoch taken at its install, and the inherit
  path reads the replaced run at the same clock; the backwards fill that hid a
  stamp ahead of the commit is gone with the stamp. On Android
  `resolveStartStamp` now refuses a stamp ahead of the wall clock for every
  start, so the replacement-only variant is gone.
- **JS.** Empty groups are rejected before any native call, so the new
  off-UI-thread error in `cancel` cannot fire on an empty snapshot.

### The native trace

`ios/SmoothClipHeroTrace.h` is bench code inside the library, compiled out
unless `pod install` runs with `SMOOTH_CLIP_HERO_TRACE=1`. This review cut it
to the two points the bench's timing reads: the hardware time of each
touch-up (`touch-ended`, a `UIApplication sendEvent:` swizzle) and the epoch
of each run a host installs (`clip-install`). The display-link and run-loop
monitor, its poke notifications and the other 19 log points are gone, as the
research switches (`SmoothClipFlushOnStart`, the snapshot probe, the view
count) already were. Once these numbers are accepted, the two that remain can
leave as well: the swizzle belongs in the example app, and `clip-install` can
be read there from Core Animation (the run's `smoothClip.geometry` animation),
with `trace.sh` and `timing.mjs` following them.
